# 0002. Deliver the interview plan to the voice agent through a custom LLM endpoint

- Status: Accepted
- Date: 2026-11-23

## Context

Each voice interview follows a plan generated by `POST /interview-plan` from the job offer and the CV. The ElevenLabs agent is shared by all sessions, so the plan has to reach it per conversation. Requirements:

- The plan must not be editable by the browser: whoever controls the agent's instructions controls an agent that spends our credits.
- During the interview the backend must take part in every turn: scoring answers with Jev (ADR 0001) and deciding whether to ask a follow-up.
- The ElevenLabs API key never reaches the browser (already the case: signed URLs).

## Options considered

1. **Overrides** (`conversation_config_override`): the browser sends the full system prompt when the conversation starts. The documentation describes it as the legacy approach and recommends dynamic variables. It needs the prompt override enabled on the agent, and then any holder of a signed URL can replace the whole prompt.
2. **Dynamic variables from the browser**: the agent prompt has placeholders (`{{interview_plan}}`) and the browser fills them in. This is ElevenLabs' recommended personalisation method and the simplest option. But the values are client-controlled: the plan travels through the browser and can be changed, and the backend does not take part in the turns.
3. **Conversation initiation webhook**: ElevenLabs asks our server for the initiation data. Not available for this use case: per the documentation it only runs for telephony and messaging channels, not for SDK or widget conversations.
4. **Opaque session id + server tool**: the browser passes an id, and the agent calls a webhook tool to fetch the plan. This depends on the LLM deciding to call the tool, adds a round trip, and the id is still client-supplied.
5. **Custom LLM endpoint in FastAPI**: the agent's LLM is our OpenAI-compatible endpoint. ElevenLabs sends every turn to it, and the backend builds the prompt from the plan it stored and calls DeepSeek. This is the pattern documented for "bring your own model", and other integrators use it to keep per-user context server-side.

## Decision

Option 5:

1. `POST /voice-session` requests the signed URL with `include_conversation_id=true`. The `conversation_id` comes back inside the URL, and the backend stores `conversation_id -> plan` (and the access code that started it).
2. The agent's prompt in ElevenLabs is a stub that only contains a marker with `{{system__conversation_id}}`. System variables cannot be set or overridden by the client.
3. ElevenLabs calls `POST /v1/chat/completions` on our backend, authenticated with a bearer secret stored as an ElevenLabs workspace secret. The backend reads the conversation id from the marker, rejects unknown ids, replaces the system message with its own interviewer prompt built from the stored plan, and streams DeepSeek's answer back as SSE.
4. All overrides stay disabled on the agent, and the browser sends no dynamic variables.

## Evidence

A local spike created a temporary agent (custom LLM pointing at a local fake server through a tunnel) and ran text-only WebSocket conversations:

- The custom LLM request carried our bearer secret and the rendered system prompt, including the real `system__conversation_id` and the dynamic variables. No other per-conversation data came in the body or headers.
- ElevenLabs prepends about 2.4k characters of its own boilerplate to the system prompt. Our endpoint can replace the system message entirely.
- With `include_conversation_id=true`, the signed URL contains `conversation_id`, it equals the id of the conversation that is actually started, and the URL is single-use: a second connection is rejected ("access link has expired or is invalid").
- A plain signed URL (the current implementation) **can be reused**: two conversations were opened with the same URL.
- A client-side prompt override on an agent without that override enabled is rejected (close code 1008, "Override for field 'prompt' is not allowed by config").
- Dynamic variables from the client were applied to the prompt and the first message (option 2 works; it was rejected for control reasons, not feasibility).

## Consequences

- **Security fix, independent of the rest:** a plain signed URL is reusable for its 15 minutes, so one quota unit of `POST /voice-session` can open several conversations. Requesting it with `include_conversation_id=true` makes it single-use. With this design, a conversation whose id the backend did not issue gets no plan and no answers anyway.
- The plan never leaves the server, and every turn passes through the backend, which is where Jev scoring and follow-up decisions will go.
- The backend must be reachable from the internet over HTTPS. For development, a tunnel (`cloudflared tunnel --url http://localhost:8000`) works; this pushes the deployment work earlier.
- New code: a streaming OpenAI-compatible endpoint, streaming support in the `LLMClient` port, and a conversation store (in memory first, Postgres later, like the quota).
- Latency becomes our responsibility: DeepSeek's time to first token is added to every turn. Measure it; buffer words ("... ") are the documented mitigation.
- Reading the conversation id from the rendered prompt couples us to that template. Keep the marker explicit (`<conversation_id>{{system__conversation_id}}</conversation_id>`) and fail closed if it is missing.
- Agent configuration (custom LLM URL, secret, stub prompt) becomes part of the deployment. Keep it in a script or document it, not only in the dashboard.

## Notes

- 2026-11-23, implementation step 2: the plan reaches `POST /voice-session` from the browser, which receives it from `POST /interview-plan`, so the user can edit it before starting. This does not weaken the decision: the plan is built from the CV and the job offer, which the user writes freely anyway, so it is untrusted data in any case. What the decision protects is the agent's instructions: the system prompt is ours, overrides stay disabled, and the plan is only inserted as size-bounded, delimited data. Storing plans server-side at generation time (returning a `plan_id`) would add state without adding trust, so it is not done.
